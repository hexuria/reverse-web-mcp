rwmcp · the execution layer

Reverse-WebMCP

WebMCP declares the actions and lets a model pick the order. This declares what those actions mean and lets a compiler pick both.

WebMCP · actions in

The app publishes what you can do. A model picks the next call, every turn, and hopes the outcome follows.

Reverse-WebMCP · outcome in

The app publishes what each action means. A model states the outcome once; a compiler derives the calls and their order.

Reversed arrow, not reversed effort. Both need the app's author to write something down — nothing here reads your API and guesses. What flips is the direction: actions → outcome becomes outcome → actions.

05 · not rivals

WebMCP is a door this walks through

An operation can be exposed several ways at once. Each door carries a cost in the world model, and the compiler picks the cheapest one this run is allowed to use.

06 · picking one

When each is the right answer

reach for MCP / WebMCP
  • The work is one or two calls, or genuinely open-ended.
  • Each step's outcome changes what the next step should be.
  • You want any MCP client — a chat app, an IDE — to use it with no engine.
  • You can't say in advance what "done" looks like.
reach for reverse-WebMCP
  • The same shape of job runs over and over, wide or deep.
  • Doing something twice would be expensive: money, email, a message.
  • Someone will ask what happened, and "the transcript" is not an answer.
  • Part of the job is waiting for the outside world.

What it can't do today

Rust onlyThere is an rwmcp command-line tool and the crate itself. No JS or Python package, no HTTP service, no MCP server exposing rwmcp to another agent.
No desktop driverScreens means a web page in headless Chrome. A native macOS or Windows app has no door.
The predicate language is smallentity(arg=value).field=value and equality, nothing else. No arithmetic, no comparisons, no negation, no "the three largest". A goal needing those can't be written as wants.
Wants must be concreteLint rejects any unbound variable, so "invoice whoever is overdue" has to become a list of names first — read from your app before compiling.
One module does call a modelThe compiler and scheduler make zero model calls — but planner.rs ships inside the engine crate and makes exactly one per goal. Skip it by supplying wants yourself.
Idempotency is your app's promiseThe compiler stamps the key. If your API ignores idempotency-key, a retry still double-sends — the ledger will record it, nothing prevents it.
~10 lines per operationEvery operation needs its x-reverse-webmcp block written once. The /annotate-world-model skill drafts them and verifies each against the running app, but somebody still reviews the result.
The evidence is narrowOne target app, five runs per cell, two models. Enough to falsify the claim, not enough to call it settled.
