01 · the claim

Thinking does not scale with the work

One model call for rwmcp whatever the depth or width. A tool loop pays roughly one per dependency level, and fourteen at three hundred rows. Medians; same app, same model, same machine.

02 · the ceiling

Execution matches a hand-written program

Arm E is a hand-written parallel script with no model in it at all — the speed of light for this app. rwmcp's execution lands within tens of milliseconds of it, which says the planning call is nearly all the wall time.

taskrwmcp executingscript ceilingdifference
T2 · ten invoices65 ms63 ms+2 ms
T4 · wait for payment658 ms695 ms−37 ms
T9 · ten chains, six deep712 ms727 ms−15 ms
T8 · three chains, six deep699 ms724 ms−25 ms
T11 · three hundred invoices302 ms126 ms+176 ms
T11 is the honest exception. The script goes 300 wide because it simply spawns 300 futures. rwmcp's API pool caps at 64 concurrent effects, so it takes three waves. That is a deliberate default, not a limit of the design — but it is slower here, and the table says so.

04 · what these numbers are not

Read this before quoting anything above

  • Five runs per cell is a smoke signal, not a proof. Three for the loop arms. One cell — the WebMCP loop on T9 — has only two, because that campaign was interrupted.
  • "One model call" is a median. Five of sixty rwmcp runs took two: T5-D-2, T8-D-4, T9-D-5, T11-D-3, T11-D-5. In each the planner's first intent failed lint and was re-asked once.
  • Do not add the thinking and executing columns for a loop. A loop's execution span covers its thinking turns too, so for the loops those two overlap and sum to more than the wall time. For rwmcp they are disjoint.
  • The pixel arm finished nothing and is not in this campaign at all.
  • The target app is in-memory by design, with 25 ms of artificial latency on every write so it behaves like a network service.
  • One app, two models. Enough to falsify the claim, not enough to call it settled.
Nothing here is taken on an arm's own word. bench verify recomputes max-parallel, plan and run time, sample and token counts, correctness against the oracle, and double-sends from the raw ledger rows, then fails if anything stored disagrees. All 143 results across both campaigns verify clean.
Sources: results/campaign-6-ours (120 runs) and results/campaign-6-loops (23 runs), both verified clean. Reproduce with make bench, then make verify RUN=results/<stamp>.
