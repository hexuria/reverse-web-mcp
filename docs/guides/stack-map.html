01 · the layers

Three layers, one boundary

The line that matters is not the crate boundary — it is planner.rs. That one module makes exactly one model call per goal, behind a Sampler trait so it is testable without a network. Everything below it is deterministic: the compiler and the scheduler take an Intent struct and never ask where it came from, and scheduler.rs says so in its first three lines. That is why "one sample per goal" is structural rather than a discipline someone maintains — there is no second place a call could come from.

02 · the crates

Five crates, and who depends on whom

embed this

crates/rwmcp

A library: world model, predicates, compiler, scheduler, ledger, effectors, and the planner. Pulls reqwest, tokio, serde, sha2. No browser. This is the product.

only if you want screens

crates/driver

Wraps chromiumoxide. Leases pages from a pool and clicks controls by accessible name.

only if you want the benchmark

crates/bench

The arms, the tasks runner, the report. Delete it and the engine still works.

the command line

crates/cli

Installs as rwmcp. Plans, prints, and runs on request — the path that needs no Rust from you.

replace with your own

crates/app

The invoicing target. In real use this is your service, in any language, reached over HTTP.

04 · the third parties

What we didn't write

in the engine
  • tokio — the async runtime
  • reqwest (rustls) — HTTP + the SSE stream
  • serde / serde_json
  • sha2 + hex — the content-addressed keys
  • thiserror, tracing, futures, async-trait
in the driver
  • chromiumoxide 0.9 — the CDP client

The one heavyweight dependency, and it's isolated in a crate you can leave out.

in the cli and harness
  • clap — the command line
  • toml — task files
  • base64, chrono, async-recursion
in the sample app
  • axum + tower-http
  • rand_chacha — seeded chaos

Yours instead, in whatever you already use.

No ORM, no message broker, no database, no vector store, no agent framework. The engine's whole runtime is an async executor and an HTTP client.

Everything else — the DAG, the edges, the keys, the ordering, the concurrency, the receipt — is derived. There is no place to hand-write a plan, and that is deliberate: the README says the world model "is never hand-authored anywhere else."

Two agents, don't merge them. The planner is a model call rwmcp makes at runtime, inside L2 — one sample per goal, a fixed system prompt, no skills involved. Your coding agent works one layer out, at setup time, and that is where /annotate-world-model and /write-wants apply. The engine itself never calls either.
