One Sample Deep

A compiler turns a goal into a dependency graph and a scheduler runs it. Planning costs one model call — in 53 of 60 runs exactly one, never more than two — whatever the depth or the width. The agent loops we compare against pay a call per dependency level, and their token bill grows with the work. Two models, one app we own, 168 runs recomputed from raw ledgers by bench verify.

the structural claim

Model calls do not grow with the work

Same app, same tasks, same harness, same commit. Only the arm changes. A loop stops to think once per dependency level and again per batch; a compiled plan thinks once and the scheduler climbs the rest.

the replication

It is not one model's habit

If only one model were tested, the obvious objection is that the result is a quirk of its habits. Swapping the model and changing nothing else leaves the shape intact. All twelve of the second model's planning runs took exactly one call — it never needed the repair call the first model occasionally did — and the loop took four to fourteen on both, task for task.

the bill

What it costs to think that many times

Model calls are the structural claim; tokens are what you are actually charged for. A loop carries its whole transcript into every turn, so the context it re-reads grows with both the number of turns and the size of the world it has looked at. A compiled plan reads the world model once.

the clock

The thinking is the cost, not the doing

Execution runs in tens of milliseconds, or in hundreds when it is waiting for the outside world. Two tasks take longer, and both are waiting rather than working: T12 is being rate-limited by the app and obeying it, and T13 is discovering a payment whose webhook was dropped. The planning call is nearly all of the wall time everywhere else, which is why a plan cache matters — and that one is measured too, in campaign-3-cache: every task planned once, then ran a second time at zero model calls, twenty-one of twenty-two correct.

what to believe

Reading it honestly

  • One call is a median, not a guarantee. 53 of 60 planning runs took exactly one call; seven took two. Every one of those seven failed the same way — the planner returned an intent with an empty list of wants, the lint rejected it, and one repair call fixed it. None took three. Under the second model all twelve planning runs took one.
  • The difference that holds is calls, not width. Parallel tool calls parallelise fine: the loop went 50 wide on the 300-row task. What it cannot do is stop thinking between levels, and every stop re-reads the transcript.
  • Correctness is close when the harness is fair. Of 48 loop runs, 45 were correct. The three that were not are the WebMCP loop on 300 rows, which hit its 40-turn budget in all three runs having created up to 283 invoices and sent none. That cap is a configuration value, not a discovered ceiling, so read it as "did not finish within the budget we gave it", not as "cannot".
  • The guarantees are structural, not prompted. Idempotency keys, spend gates, event waits and join order are inserted by the compiler, so no amount of model drift can skip them. Zero double-sends across all 168 runs is the visible consequence.
  • Repeating a chaos task does not test chaos. T5 injects a 30% send-failure rate and T12 a write limit, but both are seeded, so all five runs draw the identical failures. Those repeats measure model and network jitter, nothing about robustness to a different draw.
  • Coverage is uneven, and the table does not make that obvious. Ours ran twelve tasks five times; the loops ran four tasks three times; the second model ran four tasks three times with no WebMCP arm. Every cross-arm comparison here rests on those four tasks.
  • Wall clock has a long tail we report as medians. Two planning calls took 60 and 130 seconds against medians of 6 and 5 — single calls, no retry, gateway latency rather than extra work. Means would be badly misleading; every number on this page is a median.
  • Twelve tasks, not thirteen. T7 needs a screen — its approval step exists only as a button — and every campaign here ran the API surface. It is written and it is excluded, rather than quietly absent.
  • Five runs is a smoke signal, not a proof. Enough to see a shape; not enough to publish a confidence interval.
Five things this benchmark caught us doing wrong. A stale binary that made a smoke test measure old code. A silent fallback to a hand-written plan when the planner failed, scoring a model failure as a success. An app bug that erased payments only for the slower arms, which made the loops look worse than they were and forced a retraction of an earlier claim. A quantifier whose meaning depended on position, so "one report over ten invoices" compiled into ten reports. And an edge orientation that followed the order the wants were written in, so listing a report first produced a report over draft invoices with every check passing — found by a reviewer, not by us. Each one is fixed, pinned by a test, and disclosed here rather than quietly rerun. rwmcp --order-check now compiles a set of wants forwards and backwards and diffs the two graphs, so the last of them cannot come back unnoticed.
The pixel arm is not in this table. A screenshot-and-click loop was built and run, but only as a smoke test — two tasks, one run each, in results/screens-smoke. Both hit the 40-turn cap having finished nothing, at 762,880 and 759,148 input tokens. That is two data points with no prompt-tuning parity with the other arms, so it is reported as the straw the design exists to avoid rather than as a scalp, and it is kept out of every comparison above.
Provenance and how to reproduce

Rust workspace, every commit green through make gate: rustfmt, clippy with warnings denied, and the full test suite including in-process end-to-end runs. The target app is ours, with five doors and an oracle that counts effects independently of any arm's claim — a run is correct when the app's own final state matches the task's declared expectations, not when the arm says it finished.

Three campaigns, 168 runs, all verified clean:

  • results/campaign-7-ours — 120 runs. Arms D and E, twelve tasks, five runs each. Planner grok-4.6 at low effort.
  • results/campaign-7-loops — 24 runs. Arms B2 and C, tasks T2, T4, T9 and T11, three runs each, grok-4.6 at medium effort, 40-turn cap.
  • results/campaign-7-luna — 24 runs. Arms D and B2, the same four tasks, three runs each, gpt-5.6-luna.

The planning arm ran at low effort and the loop arms at medium, which favours the loops. Every arm reached the app over the same 25 ms-per-write latency, on the API surface only. Reproduce the three in turn:

make bench-ocx ARMS=D,E PLANNER=model RUNS=5
make bench-ocx ARMS=B2,C RUNS=3 TASKS=T2,T4,T9,T11
make bench-ocx ARMS=D,B2 PLANNER=model RUNS=3 TASKS=T2,T4,T9,T11 MODEL=gpt-5.6-luna
then make verify RUN=results/<stamp> on each, which recomputes every number here from the raw ledgers.
