03 · read this before you point it anywhere

The one command that will wipe your app

bench run is a benchmark harness, not a production runner. Before every single run it calls POST /oracle/reset on the target and then POST /oracle/chaos to install failure injection. Against a real app it will either fail on a missing endpoint or, if you were unlucky enough to implement one, reset your data and start injecting faults.

// crates/bench/src/main.rs — inside the task × arm × run loop
oracle.reset(task.seed).await?;      // ← unconditional, every run
oracle.chaos(&chaos).await?;

So there are exactly two safe ways to run real work today:

against the sample app

bench run --spawn

Starts its own app on a free port and stops it at the end. This is the benchmark, and it is the right tool for measuring.

against your app

the rwmcp command, or the crate

Both plan and run without resetting anything. The command is the quick path; depending on the crate and driving the scheduler yourself is the embedded one.

There is now an rwmcp command. It takes a goal or a file of wants, prints the plan, and only executes when you say so — which is what an agent should drive, instead of writing glue. Its exact flags are being reworked as this is written, so take them from rwmcp --help rather than from here. What has not changed: nothing runs until you ask, and the plan is printed first.
Still missing: no JS or Python package, no HTTP service, and no MCP server exposing rwmcp to another agent. Your coding agent shells out to the command or embeds the crate.
04 · the setup loop

Draft, then prove

Both skills work the same way, and the second half is the half that matters. A drafted footprint is a guess. A wrong writes list is the worst failure this design has: it deletes an edge, the plan looks more parallel, and two writes race with nothing in the output saying so.

skilldraftsthe check that ends it
/annotate-world-modelthe x-reverse-webmcp block for each operationreset, call the operation, diff the state. Every row that changed must appear in writes.
/write-wantsthe wants and forks for a goallint, read plan.render(), then compile the same wants in a different order and diff the two plans.

That last check has a history. Edges used to be oriented by the order the wants were written, so listing a report before the sends that feed it produced a report over draft invoices — committed, every check green, silently wrong. Fixed in 7ff8216, with tests that compile T3's and T7's wants both ways and assert the same DAG. The skill keeps checking anyway, because a regression there is invisible without it.

05 · wiring your agent

Claude Code, Codex, Grok Build

A skill is a Markdown file with a name and a description. Claude Code loads them by convention; every other agent reads the same file as a prompt.

Claude Code

Nothing to install

They live in .claude/skills/ in the repo and load automatically. Type /annotate-world-model or /write-wants.

For your own app's repo, copy the two folders across.

Codex

Point AGENTS.md at them

Codex reads AGENTS.md from the repo root. Add a line pointing at each SKILL.md, or paste the file's body in when you start the task.

Grok Build / anything else

Paste the file

Open .claude/skills/<name>/SKILL.md, paste the body as your opening message, then give it your OpenAPI document.

What to ask for, in either case. annotate "Read my OpenAPI at <url> and the handlers in <dir>. Draft the x-reverse-webmcp block for every write operation, then verify each one against the app running at <url> and tell me which are verified and which are still drafts."   wants "Turn this goal into wants for my world model, lint them, render the plan, and compile them in a second order to prove the DAG is stable."
06 · the whole thing

Start to finish

1

Watch it work on the sample app

cargo build --release && make bench
2

Annotate your own app

Run /annotate-world-model against your OpenAPI and your handlers. Review what it drafts; ship only what it verified.

3

Add idempotency to your writes

Accept an idempotency-key header; the same key returns the first response and changes nothing. Without this, "zero double-sends" is not true of your app, whatever the receipt says.

4

Write the glue

let world = Arc::new(rwmcp::world_from(base).await?);
let intent = Intent { goal: "…".into(), wants, ..Default::default() };
let plan = rwmcp::compile(&intent, &world, &opts)?;
let outcome = sched.run(&plan, &mut ledger).await;

Ask your agent for this too — it is the same four lines every time.

5

Read the receipt

committed: every keyed node has an ok row. need_think: it stopped at a declared fork, and yield_reason says which. error: a step failed and it names it.
