rwmcp · reverse-WebMCP · explained with pictures

rwmcp in Pictures

You tell it what should be true. It thinks once, then does everything at the same time, and hands you a receipt.

Also called reverse-WebMCP. WebMCP declares the actions and lets a model pick the order. This declares what those actions mean and lets a compiler pick both. Reversed arrow, not reversed effort — somebody still writes the declaration.
1 · the whole idea

A kitchen with one chef and many cooks

Most AI agents think, do one thing, think again, do one thing… rwmcp thinks one time, writes a plan with everything on it, and runs the plan as wide as your data allows.

2 · why it matters

Stairs versus a wide door

3 · what your app needs

Doors into your app

rwmcp never touches your code. It talks to your app the way any client would: through HTTP. Your app just needs a few doors.

  • 1
    An OpenAPI file at /openapi.json, with an operationId on every operation and small x-reverse-webmcp notes (next picture).
  • 2
    Idempotency. Every write accepts an idempotency-key header. Same key twice = return the first answer, do nothing new. This is what makes "zero double-sends" true.
  • +
    /events, a server-sent-events stream (data: {"seq","kind","entity","id"}). Without it, "wait for payment" polls instead of waiting.
  • +
    /mcp JSON-RPC door, and a web page where every control has a role and a name. Only needed for steps that exist only as a button.
4 · the notes

A sticky note on every door

Each operation in your OpenAPI gets a note saying what becomes true when you call it, what must already be true, and what it touches. That's the whole "world model". rwmcp reads it; nobody writes plans by hand.

Three more notes live at the top of the file: x-reverse-webmcp-entities (your nouns and their fields), x-reverse-webmcp-events (things the outside world does, like a payment), and x-reverse-webmcp-ui (button-only actions).

5 · what you actually do

Five steps, start to finish

1

Get the tools

A Rust toolchain (cargo). A model endpoint: an ANTHROPIC_API_KEY, or any local gateway that speaks the Messages shape (opencodex on localhost:8080 works with no key). Chrome and Docker only if you want screen steps or the sandbox.

2

Install

git clone <rwmcp> && cd rwmcp
cargo build --release
make app      # sample invoicing app on :47310
make bench    # see it work before touching your own app
3

Put the doors on your app

Serve /openapi.json with the notes. Honor idempotency-key on writes. Add /events if anything needs waiting for.

You do not write the notes by hand: run /annotate-world-model and your coding agent drafts them, then proves each one by calling the operation and diffing what changed.

4

Point rwmcp at it

let world = Arc::new(rwmcp::world_from("http://localhost:8000").await?);
let intent = Intent { goal: "invoice Acme and send it".into(),
    wants: vec!["invoice(customer=customer(name='Acme')).status='sent'".into()],
    ..Default::default() };                 // or let the planner write the wants
let opts = CompileOptions { plan_id: "job-42".into(), surfaces: vec!["api".into()] };
let plan = rwmcp::compile(&intent, &world, &opts)?;   // the ticket
let sched = Scheduler { effectors: rwmcp::default_effectors(base, world.clone(), &opts.surfaces),
    bus: Some(EventBus::connect(base).await?), pools: Default::default(),
    policy: Default::default(), recorder: Recorder::new(world.clone()) };
let mut ledger = Ledger::new();
let outcome = sched.run(&plan, &mut ledger).await;             // the kitchen
let receipt = ledger.receipt(&plan, outcome.status, outcome.yield_reason, outcome.evidence, outcome.error);
5

Read the receipt

committed means every step is proven done by its key. need_think means it stopped at a question (two customers named Acme, which one?). error means a step failed and it says which.

Two different chefs. The planner is a model call rwmcp makes at runtime (crates/rwmcp/src/planner.rs) — it turns your goal into wants, once. Your coding agent (Claude Code, Codex, Grok Build) is the other one: it does the setup, and there are two skills for exactly that — /annotate-world-model for the notes and /write-wants for the wants. Both end by checking their own work against the running app, because a drafted footprint is a guess until something proves it.
6 · does it work with my stack?

Your app: anything. The engine: Rust.

  • ✓
    Target app: framework-agnostic. rwmcp only sends HTTP requests and reads JSON. Rust, Node, Python, PHP, Go, an app that already exists: all the same to it, as long as the doors are there.
  • ✓
    Already-built app? Add the notes to the OpenAPI you already have, add the idempotency header to writes, done. No rewrite.
  • ~
    React Native / mobile. rwmcp drives your backend. It can also click a web page through headless Chrome (the a11y door). It does not drive a phone screen.
  • ✗
    Not yet: a JavaScript or Python SDK, a hosted service, or an HTTP wrapper around the engine. Today you embed the Rust crate or run the bench binary. The Python project in OSS/rwmcp is the earlier idea; rwmcp is its Rust rebuild.

8 · the words

Ten words, kid-sized

goalWhat you type. "Invoice everyone and send each."
wantOne fact that must be true at the end. The planner writes these.
intentYour goal + the wants + the forks, in one bundle.
world modelThe sticky notes on your doors, read from your OpenAPI.
planThe ticket: steps, arrows between them, a key on every write.
nodeOne step on the ticket. One HTTP call, one click, or one wait.
keyA stamp on a write so doing it twice does nothing new.
waitA step that sits until the outside world does something (a payment).
forkA question the chef agreed to be woken for. "Two Acmes, which one?"
door / surfaceHow a step reaches your app: API, MCP, or a screen.
receiptProof of what ran, recomputed from the log, never trusted on its word.
